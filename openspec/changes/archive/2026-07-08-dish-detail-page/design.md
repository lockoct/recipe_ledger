## Context

菜品详情页是应用的核心页面之一，当前采用"网络优先、失败兜底缓存"策略：每次打开页面先请求网络，失败才读 Hive 缓存。方案改为"本地优先、按天过期"，核心思路是用缓存同步日期（`yyyy-MM-dd`）判断数据新鲜度，同一天内零网络请求。

技术栈：Flutter + Provider + Hive + Dio。参考已实现的菜品列表页缓存策略（`dish_list_page`）进行设计，复用现有的 `cache_meta_box` 和 `CacheMetaUtils` 工具类。

## Goals / Non-Goals

**Goals:**
- 缓存新鲜时（同步日期 == 今天）直接返回本地数据，零网络请求
- 缓存跨天时清空该菜品的缓存，重新请求网络数据
- 页面首次加载（initState）使用本地优先策略，不走强制刷新
- 网络失败有旧缓存时兜底返回，不报错
- 复用现有的 `cache_meta_box` 和 `CacheMetaUtils` 工具类

**Non-Goals:**
- 不缓存价格历史数据（图表实时性要求高）
- 不改造菜品列表页缓存策略（本次只改详情页）
- 不支持下拉刷新（详情页无刷新 UI）

## Decisions

### 1. 缓存元数据使用独立 key

在 `cache_meta_box`（`Box<String>`）中为每个菜品详情使用独立的同步日期 key：
- `"dish_detail_<dishId>_sync_date"` → `"2026-07-07"`（同步日期）

**Why**: 不同菜品的详情数据可能在不同时间更新，使用菜品 ID 作为 key 的一部分可以精确控制每个菜品的缓存过期时间。

### 2. 菜品详情数据存储在独立 Box

使用 `HiveConstants.dishBox`（`Box<Dish>`）存储菜品详情数据，以 `dishId` 作为 key。

**Why**: 菜品详情模型（`Dish`）与列表项模型（`DishListItem`）结构不同，需要独立存储。复用现有 `dishBox`，无需新增 Box。

### 3. 缓存过期时清空单条缓存

跨天时只删除该菜品的缓存数据和对应的同步日期元数据，不影响其他菜品。

**Why**: 菜品详情数据是独立的，清空单条比全量清空更精确，避免影响其他菜品的缓存。

### 4. 网络失败时返回旧缓存

网络请求失败时，即使缓存已过期，也返回旧缓存数据兜底。

**Why**: 保证离线体验，用户至少能看到旧数据，比显示错误提示更好。

## Risks / Trade-offs

- [Risk] 今天内数据有修正（如价格录入错误后修正）→ 用户需等到第二天缓存过期才能获取更新，但按天更新的业务场景下修正概率低，可接受
- [Risk] 缓存数据量随菜品数量增长 → 每个菜品详情对象约 1KB，实际场景菜品数量有限，影响可忽略
