## Context

菜谱编辑页是菜谱管理功能的核心页面，用户通过菜谱详情页跳转进入。页面采用 Flutter + Provider 架构，使用 Hive 做本地持久化存储。页面需要同时支持新增和编辑两种模式，根据传入的 `recipeId` 参数区分。编辑模式下需要加载已有菜谱数据并回填表单。

## Goals / Non-Goals

**Goals:**
- 提供统一的菜谱新增/编辑入口，复用同一页面组件
- 支持封面图片选择、名称输入、原材料管理、富文本编辑四大编辑区域
- 表单提交前进行完整性验证，确保数据质量
- 编辑器聚焦时提供富文本工具栏，失焦时隐藏

**Non-Goals:**
- 不涉及后端 API 交互（当前使用本地 Hive 存储）
- 不涉及菜谱分享、复制、模板功能
- 不涉及原材料单位转换（统一使用"克"）
- 不涉及做法步骤中插入视频

## Decisions

### 1. 页面架构：StatefulWidget + RecipeProvider
- **决策**: 使用 `StatefulWidget` 管理页面级状态，通过 `RecipeProvider` 处理数据持久化
- **理由**: 页面状态（编辑模式、表单数据、加载状态）属于页面生命周期内状态，无需全局共享；Provider 已在本项目中作为状态管理方案统一使用
- **备选方案**: 使用 Provider 管理所有表单状态 — 但表单状态仅在页面内使用，过度抽象增加复杂度

### 2. 原材料类型：菜品关联 + 自定义输入
- **决策**: 原材料通过 `AddIngredientDialog` 添加，支持两种类型：从菜品库选择（关联 `dish_id`）和自定义输入（仅名称和用量）
- **理由**: 菜品库为原材料提供了标准化的数据源，减少重复输入；自定义类型满足非标准配料需求
- **备选方案**: 仅支持自定义输入 — 缺少菜品关联导致数据孤岛，无法统计菜品使用情况

### 3. 富文本编辑器：flutter_quill
- **决策**: 使用 `flutter_quill` 实现做法步骤和注意事项的富文本编辑
- **理由**: flutter_quill 提供开箱即用的工具栏（项目符号、数字列表、图片插入），支持 Delta 格式的序列化/反序列化，与 Hive 存储兼容
- **备选方案**: 使用 `flutter_quill` 以外的富文本库 — 项目已在使用 flutter_quill，保持一致性

### 4. 表单验证策略：提交时统一验证
- **决策**: 在用户点击提交按钮时执行所有验证（名称非空、至少一个原材料），通过 SnackBar 显示错误信息
- **理由**: 避免实时验证打断用户输入流程，提交时验证用户体验更流畅
- **备选方案**: 实时验证（输入时即时反馈）— 对菜谱编辑这种非高频操作场景，实时验证过于激进

## Risks / Trade-offs

- **[数据丢失风险]**: 用户在编辑过程中误触返回按钮可能导致未保存数据丢失 → 后续可考虑添加"确认离开"对话框
- **[富文本图片存储]**: flutter_quill 中插入的图片需要本地路径管理，需确保图片文件在菜谱生命周期内有效 → 将图片复制到应用私有目录
- **[Hive 性能]**: 富文本内容（Delta JSON）可能较大，影响 Hive 读写性能 → 当前菜谱数量有限，暂不构成瓶颈；后续可考虑图片和文本分离存储
