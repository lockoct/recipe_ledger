## Context

菜品列表页是应用的首页，当前采用"网络优先、失败兜底缓存"策略：每次打开 App 先请求网络，失败才读 Hive 缓存。方案改为"本地优先、按天过期"，核心思路是用缓存同步日期（`yyyy-MM-dd`）判断数据新鲜度，同一天内零网络请求。

技术栈：Flutter + Provider + Hive + Dio。

## Goals / Non-Goals

**Goals:**
- 缓存新鲜时（同步日期 == 今天）直接返回本地数据，零网络请求
- 缓存跨天时清空全部缓存，重新请求第一页
- 加载更多时追加数据到缓存，全量加载后标记 `fully_loaded`，避免今天内重复触发
- 筛选/搜索直接请求网络，不走缓存
- 下拉刷新清空缓存和元数据，重新请求
- 网络失败有旧缓存时兜底返回，不报错

**Non-Goals:**
- 不缓存价格历史数据（图表实时性要求高）
- 不缓存带筛选条件的结果（只有无筛选的首页列表走缓存）
- 不改造菜品详情页缓存策略（本次只改列表页）

## Decisions

### 1. 缓存元数据用独立 Box 存储

使用 `cache_meta_box`（`Box<String>`）存储简单 key-value：
- `"dish_list_sync_date"` → `"2026-06-28"`（同步日期）
- `"dish_list_fully_loaded"` → `"true"`（全量加载标记）

**Why**: 元数据轻量（2个字符串），不需要单独模型，`Box<String>` 最简单。与菜品数据 `dish_list_box` 解耦，方便单独清理。

### 2. 缓存过期时清空全部缓存

跨天时 `clear()` 全部缓存 + 重置元数据，重新请求第一页。

**Why**: 价格每天都在变，局部替换旧缓存无意义。全量清空逻辑简单，不会残留过期数据。

**Alternative**: 局部替换（只更新第一页）——但旧缓存中第二页之后的数据可能价格已变，会产生数据不一致。

### 3. 加载更多时追加缓存

`pageNum > 1` 时网络请求成功后追加到 `dish_list_box`（不清空），若 `pageNum == pages` 则设置 `fully_loaded = "true"`。

**Why**: 用户翻页后缓存累积，下次打开 App 从缓存返回时数据更多，减少翻页网络请求。全量加载标记避免重复触发加载更多。

### 4. 从缓存返回时全部返回

不走分页逻辑，直接把缓存全部数据返回，`pageNum` 根据缓存数量推算，`hasMore` 由 `fully_loaded` 决定。

**Why**: 缓存数据已经全部在本地，没必要模拟分页。用户翻到底时如果已全量加载则不再请求，否则触发网络加载更多。

### 5. 筛选/搜索不走缓存

有 `name`、`region`、`categoryId` 任一筛选条件时，直接请求网络。

**Why**: 筛选结果变化多，缓存命中率低，且缓存数据和筛选条件难以匹配，直接请求网络简单可靠。

## Risks / Trade-offs

- [Risk] 缓存数据量随时间增长（每天翻页累积） → 每个菜品对象很小（几百字节），实际场景菜品数量有限，影响可忽略
- [Risk] 今天内数据有修正（如价格录入错误后修正） → 用户需要下拉刷新才能看到修正数据，但按天更新的业务场景下修正概率低，可接受
- [Risk] `fully_loaded` 标记为 `"true"` 后，当天新增菜品无法感知 → 同上，用户需要下拉刷新；新增菜品频率低，可接受
